# Issue #51 — Add static tuple spreading to primitive prefix application

- **Issue:** https://github.com/tuncbahreadingmaterial-ops/Faraweave/issues/51
- **File status:** Active append-only decision record

## 2026-07-25 — Expand typed prefix arguments while retaining one owned operand

- **Context:** Issue #50 made tuple literals first-class values and deliberately preserved them as one argument in adjacent calls. Issue #51 must make primitive-name prefix application spread a statically typed tuple one level without moving spreading into primitive descriptors, public direct application, or scalar/vector kernels.
- **Decision:** Parsing continues to record one prefix operand and its complete span. Typed lowering recognizes a tuple operand from the syntax-independent structural node kind, derives semantic arity and ordered argument types from its immediate static children, and selects the primitive implementation before evaluation. Evaluation constructs the operand tuple exactly once, passes immutable child views into the typed-only application boundary, and releases the tuple owner after the complete application attempt. Generated C performs the same sequence by borrowing pointers into the tuple's immediate child table and releasing the table on both success and failure. Direct bracket calls retain their source arguments unchanged.
- **Provenance:** A spread call derives one semantic origin per immediate tuple element. Literal elements use their element spans; computed elements use the complete producer-expression span. The complete tuple operand remains represented by the prefix call's sole syntax argument, while the call and primitive-name spans remain separate context. Static and runtime argument-position failures select the corresponding semantic origin.
- **Failure order and ownership:** Static expansion precedes arity, signature selection, type, and proven shape validation. Runtime shape, resource, and domain checks use the already-selected semantic sequence. Borrowed scalar, vector, or nested-tuple children never copy, reallocate, retain, or independently release storage. The tuple owner remains live through application and is the only release unit, including every failure boundary.
- **Alternatives considered:** Rewrite prefix tuple syntax into an adjacent call; move spreading into `apply_primitive`; choose spreading from overload candidates; move children back out of the tuple; create shallow owning `Value` aliases; recursively flatten nested tuples; or elide construction. These alternatives lose direct-call preservation, make semantics overload-dependent, risk duplicate ownership, hide allocation/release behavior, or exceed the accepted one-level scope.
- **Rationale:** Keeping syntactic ownership and semantic arguments distinct makes static costs and diagnostics explicit. A typed-only borrowed view preserves the primitive and public API boundary while allowing vectors and nested tuples to remain in their one flat owner arena. Equivalent emitted-C child-table borrows keep evaluator/native behavior and release timing aligned.
- **Consequences or follow-up:** Empty tuples supply zero semantic arguments, singleton tuples supply one, and nested tuples remain one argument at the outer position. Computed tuple-valued producers can use the same structural-type decision when such producers are added. Faraweave deliberately differs from Anka by making expansion static, restricting it to primitive-name prefix application, preserving adjacent calls, and retaining explicit profile-v2 tuple allocation even for immediate spreading.
- **Validation/evidence:** `TUP-010-STATIC-SPREAD`, `TUP-011-SPREAD-RUNTIME`, and `TUP-013-PROVENANCE` cover evaluator semantics, static ordering, semantic spans, vector borrowing, emitted child-table views, and release order. The tuple strict-C/native contract includes equivalent prefix and adjacent journeys. Final review and isolated QA evidence are recorded in the Issue #51 pull request.
- **Supersedes:** None.
