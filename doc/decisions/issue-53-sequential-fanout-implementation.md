# Issue #53 — Implement sequential fan-out across evaluator, C emitter, and native execution

- **Issue:** https://github.com/tuncbahreadingmaterial-ops/Faraweave/issues/53
- **File status:** Active append-only decision record

## 2026-07-26 — Correct ownership of the sequential fan-out implementation decision

- **Context:** Issue #53's material implementation decision was historically appended under `doc/decisions/issue-44-explicit-sequential-fanout.md`, heading `2026-07-25 — Implement fan-out as flat source arenas with preadmitted tuple ownership`. Issue #44 owns the accepted fan-out specification, but the later parser, lowering, evaluator, ownership, resource, and generated-C implementation decision belongs to Issue #53. The Issue #44 record is protected append-only history and remains byte-for-byte unchanged.
- **Decision:** This Issue #53 record is the authoritative owner of the implementation decision. Represent fan-out syntax with brace and placeholder token categories plus flat fan-out and branch side arenas in the existing postorder rewrite pipeline. Store the fan-out operand node index on each placeholder; clone only the operand's structural type during typed lowering; and redirect runtime call preparation to immutable views of the still-owned operand. Evaluate and charge the operand once, then admit the existing positive profile-v2 tuple reservation immediately after operand completion and before branch 0. Adopt that reservation through the narrow tuple-construction entry point without a second semantic admission. Execute fully resolved and typed branches sequentially from left to right, transfer each completed independently owned result into its fixed tuple slot exactly once, and release the operand after the final transfer. On failure, release the initialized result prefix in reverse order, followed by the table and operand, without publishing a partial result. Generated C uses the same pre-branch table point, fixed-slot transfers, static last-use ownership, and cleanup order. Fan-out adds no work charge, no fan-out-specific resource event, no reference counting, no operand payload copy or reallocation, and no allocation stream beyond operand events, the existing tuple-table event, and branch events in source order.
- **Alternatives considered:** Desugar by duplicating the operand into an ordinary tuple; allocate the table after branch execution; introduce shared runtime values or reference counts; recursively evaluate a fan-out subtree; retain branch results as separate temporaries until final assembly; or add a fan-out-specific resource event. Duplication violates evaluate-once borrowing, late allocation changes observable failure order, shared ownership changes the language cost model, recursive evaluation conflicts with flat lowering and static releases, delayed transfer adds unnecessary ownership, and a new resource identity contradicts profile v2.
- **Rationale:** Flat source and typed arenas preserve Faraweave's visible data flow and existing lowering model. One preadmitted table and an initialized result prefix make ownership, costs, allocation ordinals, first-failure order, and cleanup directly inspectable and identical across the evaluator and generated C. Borrowing the single operand through ordinary call preparation avoids copies while static validation prevents the borrow from escaping.
- **Consequences or follow-up:** This record corrects ownership and discovery without rewriting the historical Issue #44 bytes or changing language behavior. Faraweave deliberately differs from Anka by retaining explicit `fanout[...]` and `{...}` branch boundaries, exactly one lexical `_` per branch, strict left-to-right execution, and an ordinary owned structural tuple. It imports no Anka bars, connected tuples, blocks, implicit grouping, callable values, or executor scheduling. Bare identity branches, owned aggregate branches, repeated placeholders, tuple-aware primitives, nested fan-out, explicit mixed spreading, and parallel execution remain outside the implementation.
- **Validation/evidence:** The `FAN-*` cases in `src/rewrite.cpp` cover grammar and spans, complete static selection, typed branch order, scalar/vector/empty/tuple operands, fixed-slot transfer, incomplete-publication refusal, reverse initialized-prefix cleanup, spreading boundaries, profile-v2 accounting, positive allocation ordinals, public-result atomicity, and ordinary-expression regressions. `tests/fanout_contract.cmake` covers public run/emit-c/build static winners, exact stdout, deterministic emitted C, strict C11 compilation, native success and prefix failure, same-address operand borrows in generated code, allocation counts, resource snapshots, and operand/table/branch injected faults. The internal fixed-slot executable fixture verifies nested tuple/vector preservation because the current public primitive set has no tuple-producing primitive. Issue #53's implementation handoff and Git history retain the exact platform validation evidence; this ownership repair claims no new runtime validation.
