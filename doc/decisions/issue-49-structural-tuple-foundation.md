## 2026-07-23 — Use owned postorder arenas and one central profile-v2 tuple reservation boundary

- **Context:** FARAWEAVE-SPEC-0006 requires the tuple foundation before tuple source syntax exists. The implementation must preserve the established direct scalar/vector `Value` API, give diagnostics independently owned structural types, validate caller-formed records before access or transfer, move nested payload ownership exactly once, release arbitrary representable nesting without recursive host-stack use, and add backend-independent tuple-table accounting without changing frozen v1 behavior. Tuple-aware parser, evaluator, generated-C, native, spreading, and provenance behavior belong to later issues.
- **Decision:** Add an owned `TypeArena` with postorder nodes, contiguous child-index ranges, a final root, structural equality, validation, and iterative exact formatting. Generalize error type contexts to own complete arenas. Keep scalar/vector roots in the existing direct `Value` fields; for a tuple root, use the top-level `Value` as the logical final root and adopt every descendant into postorder `ValueNode`, child-index, vector-payload, and tuple-reservation tables. This preserves source compatibility while exposing the same checked single-root tree and independently owned payload identities. Construction validates every child, reserves the outer immediate table, then moves children in order without recharging adopted vector or nested tuple reservations. Public validation and queries are iterative and return stable invariant, tuple path, node, edge, and access-error context. Resource-aware release first validates, threads parent indexes temporarily into already-validated inactive node fields, then performs a linear allocation-free reverse-element depth-first pass before resetting the owner. Add exact `trusted-local-v2` and `bounded-v2` profiles, a fourth optional `max_tuple_table_bytes` limit, one fixed 16-byte canonical charge per immediate element, zero tuple work, a logical zero-byte empty reservation, and one shared positive-allocation ordinal sequence across vector, tuple, and workspace boundaries. V1 tuple construction fails with structured `ProfileError(unsupported_value_kind)` before reservation or ownership transfer.
- **Alternatives considered:** Force tuples into the former container-plus-scalar-element pair; replace every scalar/vector value with an arena immediately; store recursive owning child objects; borrow diagnostic types from runtime or analysis storage; clone nested payloads into outer tuples; charge host `sizeof(Value)` or transitive payload bytes; add tuple behavior to v1; recursively validate, format, or release; or retain an allocating cleanup worklist. The former type pair cannot express ordered heterogeneous structure, a wholesale public-value cutover creates unnecessary compatibility risk, recursive or borrowed ownership obscures lifetime and stack safety, cloning and transitive charging duplicate ownership/accounting, host sizes are backend dependent, mutating v1 breaks profile identity, recursion makes valid depth platform dependent, and a cleanup worklist can fail after ownership is already committed.
- **Rationale:** Postorder tables make tag, range, edge, parentage, payload, and reservation invariants locally inspectable while keeping ownership flat. A logical tuple root in the existing top-level record avoids an unrelated scalar/vector ABI redesign while retaining one final-root index and one owner path. Central reservation and release operations make canonical bytes, limit order, failure ordinals, and charge lifetime explicit. Temporarily repurposing inactive fields only after successful validation gives reverse depth-first cleanup linear cost with no recursion, allocation, extra persistent parent table, or public representation growth.
- **Consequences or follow-up:** Public `ErrorValueType` is now a complete owned `TypeArena`; callers that inspected the former container/element pair must inspect or format the structural arena. Tuple values are uniquely movable and not implicitly copyable because their payload handles use unique ownership. Host bookkeeping used to hold node and edge vectors remains outside profile accounting, while semantic tuple-table storage is charged only by the fixed 16-byte unit. Issue #50 still owns tuple grammar and evaluator/generated/native construction, #51 owns one-level static spreading and provenance, and later tuple-producing work must use this same reservation boundary. A future clone API, tuple-aware primitive signature, persistent parent table, or physical arena coalescing requires separate scope and must preserve canonical charges and fault ordinals.
- **Validation/evidence:** Focused public conformance exercises every structural type invariant, tuple/root/edge/payload/reservation failures, nested path propagation, empty/singleton/heterogeneous/deep formatting, owned diagnostic types, arity-first direct primitive rejection, unique move/release, exact and refused charges, v1 refusal, shared and nested allocation-failure ordinals, and scalar/vector regression. The focused suite, specification traceability, strict warning/no-exception build, full Release suite, sanitizer suite, diff hygiene, and exact-head CI evidence are recorded in the Issue #49 pull-request handoff.
- **Supersedes:** None. This implements the contract selected by `doc/decisions/issue-43-structural-tuples-profile-v2.md`, heading `## 2026-07-22 — Define tuples, static spreading, flat ownership, and profile v2 as one contract`.

## 2026-07-23 — Make host failure and accounting ownership explicit at tuple boundaries

- **Context:** Independent review of the first Issue #49 pull-request head found seven conformance gaps hidden by the original passing suite: host allocation failures in type/value validation, equality, and formatting were not returned explicitly; tuple host metadata could fail before the injected semantic reservation; accounting could be released through an unrelated resource context; destruction did not refund active vector and tuple reservations by itself; duplicate physical vector buffers or tuple reservation handles could appear under distinct logical entries; root winner order inspected inactive tuple fields before final-root validity; and the shared reservation ordinal could wrap. These defects violated FARAWEAVE-SPEC-0006 Sections 4.3, 5.3, 5.4, 5.5, 6.3, 6.5, and 7.2 even though ordinary allocation and valid-value paths passed.
- **Decision:** Add explicit host-allocation failure results and deterministic host-allocation injection to structural type construction, validation, equality, type formatting, value validation, and value formatting. Preserve cheap structural winner checks before value-validation bookkeeping allocation. Establish the charged tuple reservation before fallible host metadata publication, and roll the reservation back without claiming children when metadata publication fails. Bind every active vector and tuple reservation to a shared live-byte accounting identity owned by its `EvaluationResources` context; copies and moves of that context retain the identity while independently created contexts do not. Resource-aware release rejects a different identity without mutation, while `destroy_value` releases all active transitive reservations directly through their stored identity before resetting the value. Validation rejects duplicate physical vector buffers and tuple reservation handles, including cross-kind aliasing. Root bounds and final-root identity win before inactive tuple-root payload checks. Positive reservation attempts reject an exhausted ordinal instead of wrapping it.
- **Alternatives considered:** Continue relying on throwing STL allocation and process termination; treat host bookkeeping as outside structured resource behavior; reserve all host metadata before the tuple allocation seam; use only an `accounting_active` bit; accept any caller-supplied resource context during release; retain raw pointers into `EvaluationResources`; make destruction storage-only and require a separate refund call; detect duplicate logical indexes without checking physical identities; or permit ordinal wrap because it is practically distant. Those choices make failure behavior configuration-dependent, leave uninjectable publication gaps, permit wrong-context refund or leaks after resource objects move, split exactly-once destruction across callers, admit double ownership, obscure deterministic invariant evidence, or violate monotonic allocation evidence.
- **Rationale:** A shared accounting identity is the smallest representation that remains stable when evaluator result records copy or move their resource context and allows values to refund their own active charges without an arbitrary context parameter. The tuple reservation followed by rollback gives one visible transaction boundary for semantic and host metadata failure while retaining children until commit. Explicit resource status keeps allocation unavailability distinct from malformed structural data, and ordinal preflight preserves deterministic evidence at the representational boundary.
- **Consequences or follow-up:** `EvaluationResources` now carries a shared live-byte accounting identity and is copy/move constructible but not assignable because its public live-byte reference must remain bound to that identity. `VectorValue` and `TupleTableReservation` retain shared accounting identities while active, so their accounting state remains valid after the originating resource record is moved or destroyed. The structural host-failure overloads are public fault-injection seams; ordinary overloads retain existing call syntax. Application validation translates host resource failure to `ResourceError` instead of inventing `InvalidValue`. Tuple metadata failure consumes the tuple reservation ordinal, restores live bytes, leaves children claimed, and reports that same ordinal.
- **Validation/evidence:** `TUP-003-VALUES`, `TUP-004-MOVE-CLEANUP`, `TUP-008-ALLOCATION-ORDINAL`, and `TUP-009-HOST-ALLOCATION-FAILURES` cover root winner order, inactive metadata, duplicate physical payload ownership, context-bound release, destruction refunds, moved accounting identity, ordinal exhaustion, host-allocation result propagation, and tuple metadata rollback. Final focused, Release, strict/no-exceptions, sanitizer, traceability, diff-hygiene, and exact-head CI results are recorded in the corrected pull-request handoff.

## 2026-07-23 — Complete failure-preserving queries, cleanup, and physical-owner validation

## 2026-07-23 — Use one non-throwing host-storage boundary for structural operations

- **Context:** The deterministic host-allocation injection seams did not establish behavior when the real allocator refused memory. On the pre-correction Issue #49 baseline, an isolated valid 1,048,576-node type under a child-process `RLIMIT_AS` limit reached `std::vector::reserve`; the exception-enabled build caught `std::bad_alloc` and returned `allocation_unavailable`, while the required `-fno-exceptions` build terminated with exit 134. The same throwing-storage dependency existed in adjacent structural type/value validation, equality, construction, formatting, cleanup validation, and tuple metadata publication paths. The first malloc-backed correction also exposed two review obligations: an unchecked fixed-capacity push could write beyond its allocation if a capacity proof was wrong, and the direct-return scalar/vector type constructors could not report malloc failure without disguising it as an invalid empty semantic type.
- **Decision:** Store Issue #49 structural nodes, child indexes, value payload/reservation metadata, traversal/path scratch, and formatted output in `HostArray`, a fixed-capacity plain record backed by `malloc` and released by a free-function deleter. Allocation preflight returns `size_overflow` before consuming a synthetic allocation ordinal; a real null allocation returns `allocation_unavailable`; exception-enabled and no-exception builds execute the same code. Store the allocation capacity in the private allocation header as well as the public record, make push/fill return a checked `HostResourceErrorReason`, and require production callers to consume that status or prove aggregate capacity before ownership transfer. Size type-validation traversal by `child_indexes.size + 1`, a bound that remains sufficient before malformed graphs are rejected. Represent scalar and vector type leaves allocation-free in `TypeArena::inline_leaf`, expose their uniform node view through the free `type_nodes` functions, and retain malloc-backed postorder nodes for tuple arenas. Keep formatted text, validation paths, and dynamic primitive names in owning `HostArray` fields with `string_view` or `span` projections; profile views refer only to static execution-profile names.
- **Alternatives considered:** Retain throwing standard containers with catches only in exception-enabled builds; re-enable exceptions; install `new_handler`, termination, or process-global allocation hooks; treat virtual-address overcommit as allocation success; patch only the original type-validation probe; let an unchecked push rely on every caller remaining correct; return an empty invalid arena when leaf allocation fails; change the established leaf constructors to a new result API throughout unrelated diagnostic assembly; or force a direct Linux `libgcc_s` dependency with `--no-as-needed`. Those choices make supported configurations diverge, replace explicit recoverable errors with process behavior, leave adjacent abort paths or memory corruption possible, hide resource failure as semantic invalidity, expand the API correction unnecessarily, or couple this source correction to an unrelated packaging artifact.
- **Rationale:** One malloc-backed boundary gives allocator refusal a configuration-independent, non-throwing result and keeps ownership/allocation visible. Header-authoritative capacity plus checked writes makes a mistaken or corrupted public capacity claim fail without an out-of-bounds construction. The edge-derived traversal bound is valid without depending on alias, range, or orphan checks winning first. Inline leaves preserve the small coherent direct-constructor API without any fallible allocation, while tuple shapes still use the explicit-result construction contract. Owned backing arrays let result records move without dangling their diagnostic views because moving the owning pointer does not relocate its allocation.
- **Consequences or follow-up:** `TypeArena` now has two explicit public storage forms: scalar/vector leaves use `inline_leaf`, and tuple arenas use `nodes`; callers must use `type_nodes` when they need a uniform node sequence. Structural formatting and path-bearing result records, and errors with dynamic primitive names, are move-owned because their views reference embedded `HostArray` ownership. `ResourceErrorContext::profile` is a non-owning view only because every producer uses the static text returned by `execution_profile_name`. Host bookkeeping remains outside semantic profile accounting. The canonical Linux artifact tests continue to own their direct-library contract; the structural correction does not add linker forcing for a noncanonical `-fno-exceptions` executable.
- **Validation/evidence:** A Linux-only child-process test builds the structural sources with `-fno-exceptions`, applies `RLIMIT_AS`, and proves real allocator refusal returns explicit failure for type validation/construction/equality/formatting, value validation/type/formatting/destruction/release/detach, and tuple metadata publication without a signal or abort. Focused strict Release execution passed `unit.doctest` and `unit.structural_host_allocation_refusal`. Regression assertions cover a full array and a corrupted public capacity without overwriting the stored element, a malformed type with more edges than nodes, exact synthetic overflow ordinal preservation, and moved formatting/path/primitive-name ownership. ASan/UBSan with exceptions disabled passed the focused capacity and owned-error-lifetime cases.

## 2026-07-24 — Validate physical handles before access and share the complete resource cursor

- **Context:** A later independent review found six remaining boundary defects: public host and vector pointers could be forged and were dereferenced or freed before allocator membership was known; mandatory tuple-construction cleanup still allocated and ignored failures; copied resource records shared only live-byte accounting while forking work and reservation cursors; resource creation used throwing `make_shared` and behavioral member constructors; the central raw tuple reservation entry point still admitted v1; and successful raw tuple reservations had no exactly-once release operation.
- **Decision:** Register every Faraweave host array and raw semantic buffer in one intrusive allocator ledger and identify it by payload address, storage purpose, and element type. Deleters remove a matching live record before destruction or free, and validation requires a matching record before reading headers or vector elements. Keep `EvaluationResources` a plain aggregate whose references and raw stable state identity are copied by the language-generated copy and move operations; the shared state contains allocation injection, live bytes, work, reservation ordinal, and lifetime observation. Create that state with checked `malloc`, return a resource record carrying `allocation_unavailable` when creation fails, retain states in a process-lifetime intrusive list, and free the list at normal process exit. Require v2 at `reserve_tuple_table` itself and add an owner-checked `release_tuple_table` that refunds and physically releases a positive reservation exactly once. Before tuple execution, validate every nonempty scratch owner without mutation; after that proof, use an allocation-free iterative internal destroy path for overwritten scratch and reverse failure cleanup. Preserve an invalid produced owner in its scratch slot instead of attempting unsafe cleanup.
- **Alternatives considered:** Continue deriving allocation headers from public pointers; use pointer plausibility checks; hide ownership in classes; keep the partial `shared_ptr` identity and duplicate cursors; add more user-defined resource special members; catch `bad_alloc` in a no-exceptions build; make raw tuple reservation private after it had become public; or keep validation-based cleanup and assume its allocation succeeds. Pointer plausibility does not establish ownership, classes and behavioral special members conflict with Faraweave's data-oriented constraints, partial identity breaks deterministic limits and injection, throwing allocation is not recoverable under `-fno-exceptions`, removing the public seam would evade rather than complete its contract, and cleanup cannot depend on fresh memory after refusal.
- **Rationale:** The allocator ledger makes malformed-pointer rejection precede every metadata or payload access and makes forged-pointer destruction a safe no-op. One referenced mutable state gives copies and moves exactly one work/ordinal/accounting history without per-alias behavior. Process-lifetime state identity keeps reservation refund valid after the originating context record leaves scope while retaining explicitly fallible nonthrowing creation; the state allocation is small, visible, and reclaimed at normal process termination. Prevalidation establishes the proof needed by infallible internal destruction, and reverse cleanup then has no allocator seam.
- **Consequences or follow-up:** Host allocation lookup adds a small synchronized registry search to public validation and release boundaries; semantic costs and canonical tuple charges do not change. Resource-state storage is intentionally process-lifetime rather than scoped to one alias because plain aggregate copies provide no hook for reference counting; if long-running embedding measurements show material accumulation, a future explicit evaluation-session owner may replace the registry without changing value owner identities or accounting semantics. Public malformed records are preserved on failure, while their tracked deleters cannot free an unregistered address. Raw zero-byte release is idempotent and positive raw release emits the same logical-then-physical lifetime events as value destruction. Faraweave still deliberately differs from Anka by retaining the flat postorder value arena and fixed canonical tuple-table charge.
- **Validation/evidence:** `TUP-003-VALUES`, `TUP-006-PROFILE-IDENTITY`, `TUP-007-TABLE-CHARGE`, `TUP-008-ALLOCATION-ORDINAL`, and `TUP-009-CONSTRUCTION` now cover malformed registered-handle rejection, direct v1 reservation refusal, positive and repeated raw release, wrong-owner preservation, interleaved copy/move work and ordinal state, and malformed scratch preservation. The Linux no-exceptions isolated executable constrains memory before resource creation, drives context allocation to explicit refusal, probes malformed pointers under sanitizer builds, and forces nested coordinator cleanup after real allocator refusal.

Before tuple reservation or ownership transfer, compare every physical vector payload, tuple-table reservation, and tuple metadata allocation across distinct input owners; reject any overlap while every input remains claimed and no outer charge exists. Store profile, limits, creation status, injection, live bytes, work, ordinal, observer, and a transaction mutex in one resource state. Copy and move of a resource record deliberately retain the same state, including a moved-from alias, and resource API transactions lock the shared state. Represent fixed profile and structural diagnostic text with static `string_view` data so genuine allocator refusal does not require owning string construction.

Intrusive references make state lifetime proportional to live public handles and reservations without another fallible control-block allocation; the small mechanical handle is necessary because implicit aggregate copy has no lifetime hook. Keeping the complete mutable identity behind one lock makes limits, ordinals, work, and releases one serial history. ## 2026-07-24 — Use registry-validated tokens and explicit resource-context lifetime

- **Context:** Review of the intrusive special-member correction found that public values still carried raw state pointers, the public state handle exposed a pointer constructor and retain/release primitives, and caller-forged identities could reach a refund dereference. A caller could also manually release the state behind a live behavioral handle. The handle's constructors, copy/move constructors, and destructor put ownership behavior in a Faraweave-owned C++ type, contrary to the plain-data/free-function architecture. Separately, synchronous lifetime observers ran while the shared transaction mutex was held, so a callback that charged work or reserved or released storage deadlocked. Tuple metadata-failure diagnostics also sampled the shared reservation cursor outside its transaction, allowing a concurrent vector reservation to change the reported tuple ordinal.
- **Decision:** Represent resource identity in public records only as a nonzero 64-bit token. Keep state pointers and the intrusive fixed-bucket token registry private to `resources.cpp`; before any state dereference, require both live token membership and exact binding of every public shared-state reference to the registered state. Resolve value accounting tokens through the same registry before validation, refund, or reference release, so forged and stale identities fail without dereference. Make `EvaluationResourceStateHandle` plain exposed data with no constructors, destructor, operators, or member functions. Provide explicit free `move_evaluation_resources` and idempotent `release_evaluation_resources` operations; a bitwise-copied alias shares one context lease, explicit move clears the source token, and releasing that lease makes every copy safely stale while active values retain the state until physical destruction. Dispatch observer events only after releasing the transaction mutex, using direct post-commit staging for single-storage operations and bounded unlock/dispatch/relock at aggregate cleanup transitions. Derive tuple publication and failure evidence from the ordinal stored in the successfully locked tuple reservation, never from an unlocked shared cursor.
- **Alternatives considered:** Keep public raw pointers but add plausibility checks; expose a generation beside the pointer; retain public manual state-reference functions; hide behavioral lifetime in another class; add defaulted or custom special members; make copied records independent owners; allocate a per-copy lease; invoke callbacks under the mutex and document non-reentrancy; silently skip nested callbacks; allocate an unbounded event queue during cleanup; or lock only around the tuple cursor read. Raw or manually releasable pointers preserve the forged-dereference and behind-handle-free paths. Behavioral wrappers violate Faraweave's architecture. Per-copy leases require copy hooks or another fallible allocation, while independent owners fork the shared policy and cursors. Callback restrictions make a synchronous public observer unexpectedly unsafe, allocating cleanup evidence violates the refusal contract, and a second cursor read can still identify a different reservation.
- **Rationale:** A monotonic opaque token is forgeable as data but harmless as authority: registry membership and exact record binding are the authority, and tokens are never dereferenced. One explicit context lease makes plain aggregate copies safe without hidden retain/release behavior; explicit move and teardown make ownership visible and permit prompt reclamation. Positive reservations already retain the registered state, so values can outlive the context without an exit hook or process-lifetime accumulation. Releasing the transaction before callback dispatch preserves the serialized commit point while allowing the callback to use the same context. The reservation's stored ordinal is the transaction result and therefore the only race-free diagnostic identity.
- **Consequences or follow-up:** Callers that create an evaluation context must explicitly release it, and callers that transfer the context record must use `move_evaluation_resources`; ordinary aggregate copies are non-owning aliases to the same context lease. After explicit release or move, only the token and handle fields may be inspected; resource operations return structured refusal, and direct access through the old bound shared-state references is outside the API. Resource values retain their accounting state independently and `destroy_value` remains the context-free cleanup boundary. Observer callbacks are reentrant for resource operations, but the observer context and any caller-owned objects it mutates remain the caller's synchronization responsibility. Faraweave deliberately differs from Anka by keeping the flat postorder arena, explicit canonical tuple charge, and explicit context/value lifetime boundaries.
- **Validation/evidence:** `TUP-004-MOVE-CLEANUP` uses the explicit free move and release operations and proves that an escaped value destroys safely after context teardown. `TUP-008-REGISTRY-REENTRANCY` probes forged record and accounting tokens, preservation on failed forged-owner release, copied-alias staleness, context-free destruction after release, observer reentry through charge/reserve/release/destroy and aggregate cleanup, and mixed concurrent vector/tuple ordinals with an exact gap-free sequence. The constrained-memory refusal executable explicitly releases sequential and simultaneous contexts. ASan/UBSan exercises forged and stale identities, while strict no-exception and Release suites preserve real-refusal results, v1 behavior, accounting, and platform regressions.

## 2026-07-24 — Pin resource operations and bind semantic allocation records privately

- **Context:** A fourth review found that token membership alone was not sufficient authority. Replacing a vector or tuple owner with another live token could redirect a refund, registry lookups returned raw unpinned state pointers, concurrent or observer-reentrant context release could destroy a transaction mutex still in use, token wrap could reuse a stale identity, and public resource records retained references into state that became dangling after explicit teardown.
- **Decision:** Make `EvaluationResources` a pointer-free plain snapshot plus its opaque owner and handle tokens. Every state-using operation validates the active token and record under the registry mutex, acquires an operation reference there, and retains that pin until the transaction mutex is fully unlocked and every synchronous callback has completed. Context release marks the lease inactive under the registry mutex, holds its own operation pin while waiting for the transaction boundary, and clears the public token only under synchronization. Publish accounting state while the transaction is locked before dispatching callbacks; after a callback, relock and refresh the public snapshot before continuing. Extend the existing pointer-keyed host-allocation record with private semantic owner token, canonical charge, ordinal, purpose, and active state. Vector, tuple-table, and workspace validation or release must match and atomically consume that complete binding before refunding bytes or dropping the allocation reference. Issue tokens under the registry lock and permanently exhaust the sequence at the unsigned boundary instead of wrapping.
- **Alternatives considered:** Trust any currently live owner token; compare only public metadata; return an unpinned state after registry lookup; keep states forever; use pointer-bearing public records; reuse wrapped tokens; invoke observers while holding the transaction mutex; or add an allocating side map for semantic ownership. Those choices permit refund redirection, stale-state dereference, locked-mutex destruction, dangling public access, stale identity reuse, observer deadlock, or an additional failure and allocation seam.
- **Rationale:** The allocator record already supplies O(1) pointer membership and exact physical identity, so extending it keeps semantic authority private without another allocation. Operation references are the minimal explicit lifetime proof across unlock/callback/relock transitions. A value snapshot remains safe to inspect after teardown, while `refresh_evaluation_resources` provides synchronized access to the shared counters for live contexts.
- **Consequences or follow-up:** Plain aggregate copies are snapshots and non-owning aliases of one explicit context lease; callers refresh an alias when they need current shared counters and use the observer setter for synchronized observer publication. Direct public snapshot mutation is not a concurrent state API. A semantic value still retains its originating state after context teardown and context-free destruction consumes the private allocation binding. Faraweave continues to differ from Anka through its flat postorder ownership and fixed canonical tuple charge.
- **Validation/evidence:** Regression coverage substitutes between two valid live contexts and proves both accounting records and storage are preserved, races explicit release across threads, releases the context reentrantly from a lifetime observer, verifies a gap-free mixed concurrent allocation sequence, and drives a synthetic token cursor through its final two identities into permanent exhaustion. Focused and complete validation evidence is recorded in the final Issue #49 handoff.

## 2026-07-24 — Make shared policy authoritative and semantic bindings implementation-private

- **Context:** A fifth review found that the public host-storage header exposed the complete semantic allocation record and its bind, authenticate, and consume operations, allowing callers to manufacture or deactivate reservation authority. It also found that ordinary resource-operation entry copied profile, limits, creation status, and failure injection from an arbitrary public alias into shared state, so a stale trusted snapshot could roll back a newer bounded policy and bypass its limits.
- **Decision:** Keep the generic host-allocation safety ledger but move its record definition, semantic fields, purpose tags, release callback, and bind/match/consume functions into implementation-private source and header files. Public storage templates see only generic allocation snapshots and free functions. Add a monotonically versioned configuration snapshot to resource state and public records. Ordinary operation entry always refreshes profile, limits, creation status, failure injection, observer, counters, ordinal, and version from shared state, and operation exit publishes only the mutable accounting counters. Publish policy only through `update_evaluation_resource_configuration`; it requires the caller's version to match, increments on success, refreshes and reports `stale_snapshot` on mismatch, and reports exhaustion instead of wrapping. Observer publication remains a separate explicit setter.
- **Alternatives considered:** Keep semantic metadata public with documentation, add a public capability token, let last operation entry win, infer configuration changes by comparing snapshots, or automatically merge individual fields. Documentation does not constrain authority, a public constructible token is forgeable, and implicit publication or merging makes stale writes and mixed-policy states possible.
- **Rationale:** Semantic reservation identity is Faraweave implementation authority, not generic host-storage data. A private intrusive record preserves one allocation and the existing pointer-keyed lookup cost. Optimistic version checking makes configuration publication explicit and deterministic while ordinary operations remain safe even when aliases are stale.
- **Consequences or follow-up:** Direct mutation of public policy fields edits only that snapshot until the explicit update succeeds. A stale update does not publish any field and refreshes the caller to the authoritative snapshot. Callers that need current counters or policy may refresh explicitly; normal operations refresh automatically. This remains deliberately different from Anka where Faraweave's resource admission, canonical tuple charge, and host-allocation identity are explicit product contracts.
- **Validation/evidence:** `TUP-008-ALLOCATION-ORDINAL` proves a stale trusted alias cannot bypass a newer bounded work limit, proves stale explicit publication is rejected and refreshed, and proves a current explicit update plus refresh propagates. The obsolete-surface contract rejects semantic authority identifiers in the public host-storage header, while malformed-value and live-owner substitution tests continue to prove public metadata cannot authenticate or redirect refunds. Strict no-exception, invalid-value sanitizer, focused TUP, and full Release validation cover the private ledger and synchronization paths.

## 2026-07-24 — Make tuple profile admission and workspace release authoritative

- **Context:** A sixth review found that `make_tuple_value` and the tuple execution coordinator could inspect a stale public profile snapshot or validate and execute elements before consulting the locked authoritative state. A malformed zero-byte workspace could also carry non-null storage from another semantic allocation; releasing it skipped binding authentication and reset that storage while holding the transaction mutex, which could consume another owner and self-deadlock in abandoned-allocation cleanup.
- **Decision:** Pin and lock the resource state at tuple-construction entry, refresh the public snapshot, and decide configuration and v1 tuple refusal before inspecting elements. Keep the transaction through element validation and outer tuple admission by sharing a locked reservation helper, then publish accounting and unlock before lifetime observation. Apply the same authoritative profile gate before tuple element execution. Make workspace release return an explicit result and accept only the exact empty form (null storage, zero bytes, zero owner, no ordinal) or a positive reservation whose private semantic binding, owner, purpose, bytes, ordinal, and available accounting all match before any mutation or reset.
- **Alternatives considered:** Trust the caller snapshot; refresh without holding the transaction through admission; hold the mutex while invoking tuple element executors; keep a void best-effort workspace release; or treat any zero byte count as empty. These choices preserve stale-policy races, deadlock nested resource operations, or let malformed public metadata consume unrelated ownership without reporting refusal.
- **Rationale:** The locked profile check and admission form one observable policy decision while the existing post-commit observer boundary remains reentrant. Exact workspace shapes make zero-byte idempotence explicit and ensure every positive reset follows successful private binding consumption.
- **Consequences or follow-up:** `release_workspace` callers can now distinguish success from malformed or mismatched ownership. Tuple validation may hold the resource transaction longer, but performs no semantic allocation until the outer reservation and prevents concurrent configuration publication from changing the admission decision midway. Faraweave continues to differ from Anka through explicit profile-version admission and canonical tuple-table accounting.
- **Validation/evidence:** Stale v2 aliases observe authoritative v1 refusal before malformed-input validation or executor invocation; stale v1 aliases observe authoritative v2 and proceed. A concurrent profile publication/construction probe accepts only serialized v1 refusal or v2 construction. A same-context malformed zero workspace carrying active tuple-table storage is refused without deadlock, mutation, binding loss, or accounting change, then releases correctly through the tuple API.
