# Issue #50 — Add tuple literals across evaluator and native execution

- **Issue:** https://github.com/tuncbahreadingmaterial-ops/Faraweave/issues/50
- **File status:** Active append-only decision record

## 2026-07-25 — Lower tuple literals as flat typed construction nodes and move values only at admission

- **Context:** Issue #49 established structural tuple types, uniquely owned value arenas, profile-v2 accounting, and transactional tuple construction without adding source syntax. Issue #50 must connect square-bracket literals to every execution surface while keeping adjacent bracket calls unambiguous and without adding automatic spreading.
- **Decision:** Parse a `[` in expression position as a tuple literal and an immediately adjacent primitive name plus `[` as the existing direct call. Store tuple nodes separately from contiguous element-index and element-span arenas. Derive each tuple's complete `TypeArena` from already-lowered child types in source postorder, without evaluating child values. During evaluation, move each completed child owner left to right into one tuple-construction scratch range, admit the outer table only after all children exist, and publish only the completed owner. Generated C uses deterministic parent-linked tuple tables with the same fixed 16-byte semantic charge and shared positive allocation ordinal as the evaluator. Validation, canonical formatting, and reverse cleanup traverse those links iteratively; there is no reference counting or recursive host-stack ownership.
- **Alternatives considered:** Reinterpret every square bracket as a call; add tuple values without structural lowering; derive types from evaluated children; spread tuples in direct calls; recursively own or traverse generated-C children; charge `sizeof(FaraweaveValue)`; or flatten tuple formatting. These choices make `[]` ambiguous, violate value-independent analysis or Issue #50's non-goal, introduce depth-dependent failure, expose backend layout as language accounting, or lose structure.
- **Rationale:** Separate flat syntax and provenance arenas preserve exact whole-expression and child origins while keeping node records shallow. Postorder typed construction makes costs and dependencies visible. Moving only at the existing Issue #49 admission boundary gives one ownership transfer and one cleanup path. Parent-linked generated storage preserves deterministic iterative traversal without runtime reference counting.
- **Consequences or follow-up:** `add[]` remains a zero-argument adjacent call, standalone `[]` is an empty tuple, and a form such as `inc[[1 2]]` supplies one tuple and fails ordinary type selection. The default tuple-capable surface uses `trusted-local-v2`; explicit v1 evaluation rejects the earliest tuple-producing span. Prefix spreading, destructuring, tuple-aware primitives, mutation, and allocation elision remain follow-up work. Faraweave deliberately differs from Anka through static structural types, explicit direct-call preservation, flat ownership, versioned resource charges, and structured provenance.
- **Validation/evidence:** Focused parser/lowering snapshots, canonical evaluator results, v1 refusal, bounded-v2 exact limits, injected vector/inner-tuple/outer-tuple allocation boundaries, strict C11 compilation, native differential output, and the final review and isolated QA reports are recorded in the Issue #50 pull request.
